# Технический аудит `info_actions_2025`

Дата аудита: 1 сентября 2026 года  
Формат: статический аудит репозитория без изменения исходного кода

## 1. Резюме

Проект представляет собой Vue 3 SPA-островок с карточками акций, встроенный во внешний landing-builder. Основной поток данных понятен: глобальный конфиг → фильтрация по датам → нормализация фильтров → табы и карточки. Компоненты небольшие, аналитика и clipboard-логика вынесены в директивы.

Текущее состояние нельзя считать production-ready с инженерной точки зрения: репозиторий не содержит воспроизводимого контура сборки и качества, схема промо-данных не валидируется, а в UI присутствуют подтверждённые проблемы доступности и идентичности DOM-элементов.

**Итоговая оценка: 5/10 — работоспособный виджет с высоким операционным риском сопровождения.**

Главные приоритеты:

1. Зафиксировать воспроизводимую сборку и обязательные проверки.
2. Устранить `v-html`, неуникальные ключи и дублирующийся `id`.
3. Ввести схему и автоматическую валидацию промо-конфига.
4. Исправить клавиатурную доступность табов.
5. Убрать лишние зависимости и генерируемые артефакты из исходного контура.

## 2. Область и методика

Проверены:

- `package.json` и фактически установленные зависимости;

- данные 23 промо-записей на дату аудита.

Не проверялись из-за отсутствия инфраструктуры проекта:

- unit/component/e2e-тесты;

- browser/Lighthouse-проверка;
- сетевой аудит CDN-ссылок;
- `npm audit`: lock-файл отсутствует, поэтому результат не был бы воспроизводимым.

## 4. Детальные находки

### P0. Нет воспроизводимого инженерного контура

**Доказательства**

- `package.json` содержит только зависимости и не содержит `scripts`.
- Нет `package-lock.json`, `yarn.lock` или `pnpm-lock.yaml`.
- Нет конфигураций Vite/Webpack, ESLint, Stylelint, Prettier, TypeScript/jsconfig и тестового раннера.
- Фактически установленные версии уже отличаются от минимальных версий диапазонов: например, `@vueuse/core` 13.9.0 при `^13.7.0`, `dayjs` 1.11.21 при `^1.11.13`, Vue 3.5.41 при `^3.5.28`.

**Почему это важно**

Новый разработчик или CI не может выполнить документированный набор команд и доказать, что исходники компилируются. Без lock-файла повторная установка может дать другое дерево зависимостей.

**Рекомендация**

Определить используемый внешний сборщик, добавить README с контрактом интеграции и команды `dev`, `build`, `lint`, `typecheck`, `test`. Зафиксировать один package manager и lock-файл. Если сборка принципиально живёт в отдельном репозитории, её версию и точку входа необходимо явно задокументировать.

### P1. Потенциальный XSS через `v-html`

**Доказательство:** `site/coral.ru/js/Vue/components/Card/Card.vue:84-85` выводит `name` и `description` через `v-html`.

Сейчас данные задаются локальным `config.js`, поэтому непосредственный риск ограничен правами на репозиторий. Однако источник подключён через глобальный `window._promotion_settings`; при переносе данных в CMS или CDN значение становится границей доверия.

**Рекомендация:** заменить HTML-разметку на текст. Если требуется `<br>`, хранить строки массивом или санитизировать строгим allowlist-парсером до передачи компоненту. Регулярное выражение не должно считаться полноценной HTML-санитизацией.

### P1. Нарушение идентичности элементов Vue и DOM

**Доказательства**

- `App.vue:64` использует `:key="promotion.name"`.
- В данных два объекта с именем `Отдых ближе, чем кажется...`.
- `Card.vue:118` создаёт `id="popup-trigger"` внутри `v-for`; при нескольких карточках без URL ID повторится.

**Рекомендация:** сделать `id` обязательным полем промо-схемы и использовать его как Vue key. `popup-trigger` заменить классом или генерировать уникальный ID только при реальной связи с `label`/ARIA.

### P1. Промо-конфиг не имеет исполняемой схемы

Автоматическая проверка 23 записей выявила:

- 15 записей с истёкшим `promo_end` на дату аудита;
- 8 записей без даты окончания;
- 1 дублирующееся имя;
- 1 URL изображения с необработанным пробелом;
- 3 URL изображения с `%`, не образующим валидный percent-escape;
- 1 переход с пробелами вокруг `banner_on_site = ...`;
- 1 запись с текстом `Бессрочно` при заданной конечной дате;
- 18 записей без `entry_point`;
- поле `ligal` содержит устойчивую опечатку вместо `legal`.

Ссылки на проблемные данные: `site/coral.ru/js/config.js:71`, `:84`, `:109`, `:149`, `:160`, `:172`, `:193-202`.

**Рекомендация:** описать `Promotion` через TypeScript либо JSDoc + runtime-схему. Проверять обязательные поля, уникальность ID, даты, URL, согласованность `promo_end`/`promo_end_text`, наличие аналитических атрибутов. Запускать валидатор до сборки и падать при ошибках.

### P1. Табы недоступны с клавиатуры

**Доказательство:** `Tabs.vue:17-29` реализует переключатели как `<li @click>`, без `button`, `tabindex`, keyboard handlers и ARIA-состояний.

**Рекомендация:** использовать `<button type="button">` внутри списка. Для полноценного tab pattern добавить `role="tablist"`, `role="tab"`, `aria-selected` и управление стрелками; для простой фильтрации допустима группа обычных кнопок с `aria-pressed`.

### P1. Хрупкие границы интеграции

**Доказательства**

- `App.vue:10` читает `window._promotion_settings ?? []` и молча показывает пустой экран при ошибке порядка загрузки.
- `main.js:7` импортирует `../../../../usefuls`, которого нет в границах репозитория.
- `main.js:10` ожидает `hostReactAppReady()` без timeout/fallback.
- Отдельные defer-скрипты в `markup/info-actions.html:8-9` создают неявный контракт порядка загрузки.

**Рекомендация:** оформить адаптер окружения с явной проверкой входных данных и состоянием ошибки. Внешний helper сделать package/workspace-зависимостью либо документированным API сборщика. Для ожидания host-приложения предусмотреть диагностируемый timeout.

### P2. Аналитика может быть неполной и расходиться между брендами

**Доказательства**

- Логика бренда определена тремя разными выражениями в `App.vue:49`, `entry.directive.js:7` и `ymbonus.directive.js:7`.
- В `entry.directive.js:8-10` обе ветки имеют одинаковый goal, но разные counter ID.
- 18 из 23 записей не имеют `entry_point`; директива в таком случае не инициализирует обработчик.
- `ymbonus.directive.js:50` удаляет DOM-элемент из `WeakSet` при unmount, поэтому повторное создание карточки позволяет повторно отправить impression.

**Рекомендация:** централизовать brand/metrics config и формализовать семантику impression — один раз за DOM-жизнь, сессию или промо-ID. Валидатор должен явно разрешать либо запрещать отсутствие `entry_point`.

### P2. Лишняя реактивная и DOM-работа

**Доказательства**

- `App.vue:61` ставит `:key="currentFilter"` на весь `<ul>`, из-за чего список полностью пересоздаётся при смене фильтра.
- Промо-конфиг обёрнут в глубокий `ref`, хотя после чтения не изменяется.
- Фильтр свежести вычисляет текущее время внутри функции, но computed не имеет реактивной временной зависимости: открытая страница не обновит состав акций при наступлении даты.
- В каждой карточке рендерятся обе брендовые SVG-иконки, одна скрывается CSS.
- `ant-design-vue` используется ради tooltip/button, что требует отдельного анализа реального вклада в bundle.

**Рекомендация:** убрать key с контейнера, нормализовать данные один раз, хранить их как readonly/shallow state, добавить реактивный `now` с разумным интервалом, рендерить одну бренд-иконку. Решение по Ant Design принимать после bundle analysis, а не по предположению.

### P2. Директивы и зависимости требуют упрощения

**Доказательства**

- Собственная clipboard-директива использует deprecated `document.execCommand('copy')` как fallback.
- `updated()` пишет `dataset.clipboardText`, но обработчик читает `binding.value`, поэтому атрибут не участвует в копировании.
- В зависимостях одновременно присутствуют `copy-to-clipboard`, `vue-clipboard` и собственная clipboard-реализация; импорты первых двух в исходниках не найдены.
- Cleanup-состояние хранится на DOM-элементах под несогласованными строковыми полями.

**Рекомендация:** выбрать одну реализацию clipboard, удалить неиспользуемые пакеты после проверки внешнего builder-кода, а внутреннее состояние директив хранить под `Symbol`. Ошибка копирования должна иметь видимую обратную связь.

### P2. Репозиторий хранит производные артефакты

В Git отслеживаются десятки Next.js chunks и CSS-файлов в `dev/`, а также собранные CMS-файлы в `@CMS/`. При этом `.gitignore` исключает только `node_modules`.

**Риск:** исходники и собранная CMS-копия могут разойтись; code review перегружается минифицированным кодом; неясно, какой артефакт является источником истины.

**Рекомендация:** документировать назначение каталогов. Если это генерируемый output — исключить из Git и собирать в CI. Если CMS требует хранить артефакты — добавить проверку, что повторная сборка не создаёт diff.

### P3. Поддерживаемость и стили

- В проекте смешаны двойные/одинарные кавычки, разные отступы и соглашения об именовании.
- `Card.scss` содержит пять `!important`, что указывает на конфликт локальных и host-стилей.
- Брендовый класс передаётся каждой карточке и табам вместо одного атрибута на корневом контейнере.
- В `Tabs.vue` props не типизированы поэлементно; в `Card.vue` props не имеют обязательности и явных defaults.
- Нет пустого, loading и error-состояний.
- `site/sunmar.ru/landing.page.json` содержит пустой список секций — поддержка второго бренда в данном репозитории фактически не завершена либо не документирована.

## 5. Что прошло проверку

- Рабочее дерево до создания отчёта было чистым.
- Все проверенные `.js`-файлы синтаксически валидны (`node --check`).
- Оба `landing.page.json` корректно парсятся как JSON.
- Установленные top-level зависимости разрешаются через `npm ls --depth=0`.
- Внешние ссылки открываются с `rel="noopener noreferrer"`.
- Таймер в `Card.vue` очищается при unmount.
- Директивы снимают созданные event listeners/observer при unmount.
- Фильтр дат отклоняет невалидные даты и поддерживает отсутствие одной из границ.

Это не заменяет сборку и browser-тестирование.

## 6. План исправлений по спринтам

### Спринт 1 — стабилизация сборки и данных

Цель: сделать состояние проекта воспроизводимым и предотвращать публикацию некорректного конфига.

- определить и документировать внешний build pipeline;
- добавить package-manager lock-файл и npm scripts;
- добавить валидатор `Promotion` и стабильный `id`;
- исправить найденные URL, даты и аналитические поля;
- добавить CI-команды: install → validate config → lint → test → build.

**Критерий готовности:** чистый checkout устанавливается и проверяется одной документированной командой; некорректная промо-запись блокирует сборку.

### Спринт 2 — безопасность и корректность UI

- убрать/санитизировать `v-html`;
- заменить повторяющийся DOM ID;
- исправить keys и убрать принудительный remount списка;
- переделать табы на семантические кнопки;
- добавить empty/error-состояния и timeout интеграции с host.

**Критерий готовности:** нет duplicate key/ID, интерфейс полностью управляется клавиатурой, недоверенный HTML не исполняется.

### Спринт 3 — архитектура и аналитика

- централизовать brand config и отправку метрик;
- определить правила дедупликации impression;
- убрать глобальный конфиг либо изолировать его адаптером;
- оформить внешний `usefuls` как явную зависимость;
- нормализовать промо-данные один раз на входе.

**Критерий готовности:** бренд и метрики имеют один источник истины; сбои host/config дают диагностируемое состояние.

### Спринт 4 — тесты и оптимизация

- unit-тесты фильтра дат, нормализации и валидатора;
- component-тесты табов и карточки;
- e2e smoke для Coral/Sunmar и query `mw=true`;
- bundle analysis перед заменой Ant Design;
- принять решение по `dev/` и `@CMS/`;
- сократить `!important` и унифицировать style tooling.

**Критерий готовности:** критические пользовательские сценарии и промо-данные защищены автотестами; размер bundle и generated artifacts контролируются.

## 7. Рекомендуемый минимальный quality gate

Перед публикацией должны обязательно проходить:

1. детерминированная установка по lock-файлу;
2. валидация схемы промо-конфига;
3. ESLint + `eslint-plugin-vue`;
4. Stylelint для SCSS;
5. Vue typecheck через `vue-tsc` либо проверяемый JSDoc/jsconfig-контур;
6. unit/component tests;
7. production build;
8. smoke-тест готового CMS-артефакта без diff относительно исходников.

## 8. Вывод

Главная проблема проекта — не объём или сложность Vue-кода, а отсутствие проверяемого инженерного контракта вокруг него. Исправление отдельных компонентов без стабилизации сборки и схемы данных даст временный эффект. Рациональный порядок: сначала воспроизводимость и валидация, затем безопасность/доступность, после этого архитектурное упрощение и оптимизация.
